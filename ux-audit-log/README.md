# UX Audit — Case Log

This folder is a running log of the hands-on testing done against the Lilla P B2B wholesale test instance (`https://test.lillap.com/`), as part of the Chapter 1 UX audit. Each entry below is one test case: a specific task flow, walked through step by step, with a short summary of what was found. Screenshots and a full step-by-step account for each case live in `cases/` and `screenshots/`.

This log is a working document, not the final report. Findings and screenshots are captured here first, case by case, across desktop, tablet, and mobile; the site's Chapter 1 content (`data/phases.js`) and its screenshots are only updated in a separate, later pass, once a batch of cases has been reviewed together — see `documents/ux-assessment.md` for the full working method. This also means the material below isn't tied to a single report: the same case log could feed more than one report or deliverable.

This is a fresh round of testing, starting from Case 01.

## How to read this log

Each case below is either a **pass** (the flow works as a buyer would expect) or an **issue** (something broke, confused, or misled during the flow). Each case also gets a first-pass **Priority** (High / Medium / Low), following the Evidence model in `documents/ux-assessment.md`. Severity/effort scoring beyond that is intentionally left out of this log — full triage happens later, once the audit pass is done. This is raw field notes: what we tried, what we saw, in what order.

## Cases

### Case 01 — Login screen: cross-area review

**Status:** Issues found — no blocker on the primary path, but a silent dead end on user error.

Reviewed the `/login` screen against all three methodology areas at once. Submitting the form empty gives zero feedback (not even a network request). A malformed, non-email string is accepted with no format check and, after a few unexplained seconds of loading, redirects to a full "Complete your registration" form with the broken string baked into a disabled field. Keyboard navigation (Tab + Enter) works correctly through the form, and the app is intentionally English-only, so neither of those turned out to be real issues. Retested at tablet (768px) and mobile (375px) with Claude's built-in browser (real viewport emulation): tablet fully reproduces desktop's behavior with no responsive-specific issues, and mobile's static layout is equally clean, though its interactive behavior wasn't directly re-confirmed at that width — see the case for why. None of this blocks a user who enters a correct, registered email — hence Medium priority — but it's a rough first impression of the app.

### Case 02 — Application landing page / Default report (Fall 2026)

**Status:** Issues found — a reproducible, always-visible search defect on the app's highest-traffic screen, plus an icon-vocabulary consistency issue spanning multiple controls.

Walked through the first screen a sales rep or buyer sees after logging in: the Fall 2026 linesheet report, which auto-executes and lands the user there directly. Refresh, full-report scrolling, and the search/filter logic itself all work correctly — a nonsense-string search, a real search ("Tie", "Knit"), and clearing the search all behave as expected. But a "No results found in this report." message renders unconditionally at the end of every search's results list, even directly beneath genuine matches — a clean, single search for "Tie" reproduces it immediately, so it's a real, always-on display defect, not an edge case. Separately, three controls on this screen reuse icon glyphs that already mean something else on the same screen: the header star ("Select All") next to each product's own genuine per-item favorite star; the header X ("Unselect All") next to the X that collapses the left nav panel; and that same panel's X/hamburger toggle, which works correctly but borrows icons whose conventional meaning ("close", "open menu") doesn't quite match what they do here. Everything else tested — the account-name "Select your customer" panel, the "Show Favorites" toggle, all three report View modes, and panel collapse/reopen — worked correctly. Desktop only for this case; tablet and mobile are a follow-up.

### Case 03 — Navigation structure: left panel & user menu

**Status:** Issues found — a misleading section label, a data-accuracy bug where the MY ACCOUNT screen can keep showing a previous customer's real address and orders under a newly selected customer's name, three Low/Medium-priority consistency issues on the same user/account control, and — from a later keyboard-only follow-up — a hard dead end where a keyboard-only user cannot change either the selected season/lineheet or the selected customer. Confirmed consistent across desktop, tablet, and mobile for the original mouse-driven pass; the keyboard follow-up was desktop-only. Priority: High.

Reviewed the left navigation panel (present on every authenticated screen) and the top-right "Alan Jalife" user menu: what each of the panel's seven sections contains, how reporting, customer-account administration, and Lilla P's own back-office administration are each grouped, and whether labels stay clear both expanded and collapsed. The panel itself is a clean, predictable single-open accordion, and ADMINISTRATION correctly separates Lilla P's own back-office functions (Manage users, Manage reports, Manage assets) from any single customer's data. But "MY ACCOUNT" is misleadingly named: every item under it requires a customer to be selected first and then shows that customer's orders and payments, not the logged-in Sales Rep's own — confirmed end to end via the "customer must be selected" modal, a selected test customer, and the resulting `/my-account/orders` screen showing that customer's sales orders. Retested at tablet (768px) and mobile (375px): both reproduce desktop's behavior exactly, with mobile adapting the left panel into a full-screen overlay rather than a sidebar — a sensible adaptation, not a bug; the mobile pass needed the same joint testing method as Case 01 and Case 02, since the built-in browser's mobile-click limitation reproduced again. A follow-up test of customer selection via the user menu's search box (rather than its "Recent customers" list) confirmed the search itself works correctly — it matches anywhere in a name across the full customer base, not just the nine recent entries — but surfaced a more serious, unplanned finding: switching the selected customer can leave the MY ACCOUNT screen showing the *previous* customer's real address and orders under the *new* customer's name and heading, sometimes correcting itself after a couple of seconds and sometimes persisting until a manual page reload. This was reproduced 3–4 times across different customer pairs, with a full reload always restoring correct data — confirming it's a refresh-timing bug, not a data-storage problem — and it's serious enough (a Sales Rep could read and act on the wrong customer's real order history) to push the case's overall priority to High. Two smaller, related issues also turned up on the user/account control itself: its "Recent customers" list does show a loading spinner while it fetches — Claude eventually captured it directly on screen — but the spinner is centered in the full viewport rather than near the list and blends into the dark overlay behind the menu, so it read as missing entirely until the UX Assessment Lead caught it live during the mobile follow-up (Low priority, per the UX Assessment Lead); and the control itself changes appearance between its closed state (a name or initials) and its open state (a generic, unrelated icon), across all three viewports. A final check answered a direct question from the UX Assessment Lead about the drawer's own close control: the "X" that closes the user panel sits at the drawer's inner edge (top-left) rather than mirroring its trigger's outer-edge position (top-right), and re-clicking the trigger doesn't toggle the drawer closed — though clicking the dimmed backdrop does, so a working fallback exists.

A later, separate pass tested whether these same two panels are actually operable without a mouse, using genuine Tab/Enter/Escape key presses on the user's real desktop browser rather than clicks. The left panel's seven section headers turned out to be a genuinely well-built keyboard pattern — real buttons, correct tab order, correct ARIA, visible focus outlines, correct Enter-key activation — and ADMINISTRATION's own three sub-items go a step further and are properly keyboard-reachable and operable too. But LINESHEETS, the one section open by default on every fresh page load, uses a different, non-interactive markup for its own four items (Spring 2027, Holiday 2026, Fall 2026, In Stock): none of them can receive keyboard focus at all, so a keyboard-only user can never change which season or lineheet they're viewing. The user menu fared worse: opening it doesn't move focus inside (a keyboard user instead has to tab through most of the page header behind it first to reach the drawer's own controls), and once there, neither the default "Recent customers" list nor a typed search's results can be reached or selected by keyboard — the exact same non-interactive-row pattern as LINESHEETS' season list — meaning a keyboard-only Sales Rep has no way to select a different customer at all. Escape doesn't close the drawer, and it has no focus trap: tabbing past its own "LOG OUT" button lands back in the product grid behind it while the drawer is still visibly open. Together, these mean a keyboard-only user is fully blocked from the two things this app's navigation model revolves around — which season/lineheet, and which customer — pushing two more Findings to High priority alongside the data-accuracy bug above.

### Case 06 — Style cards: view formats, color/size/price consistency, and image browsing

**Status:** Closed — minor issues only. Desktop, tablet (768px), and mobile (375px) all hold up well: the view formats are genuinely distinct at every width, data is consistent, and color browsing and favoriting work throughout. A closing icon-consistency check turned up two icons (the card's drawer-entry icon, and mobile's "..." menu icon) that are static images outside the app's real icon system, with a measurable color mismatch and no single consistent "more options" icon across the product. Priority: Low.

Reviewed how style cards behave on the Fall 2026 linesheet report: the three advertised View formats (Gallery, Standard, Extended), whether color/size/availability/price data agrees across formats, whether a style's photos can be browsed and enlarged per available color, and how a card hands off into the right-side detail drawer (the drawer's own content is Case 07's job, not this case's). On desktop, all three View formats work correctly and are genuinely distinct: Gallery (the default, photo-forward and collapsed), Standard (three cards per row with the per-color table already expanded), and Extended (one full-width row per style, price and color name repeated per row) — switching between all three, in every direction, updated both the layout and the active-state highlight correctly every time. A style's photos across every available color can be browsed directly from the card by hovering and using the left/right arrows, confirmed crossing from one color into another within a single sequential set of photos; the lightbox shows the same content and pages the same way, handling both a style with many photos (14 confirmed) and one with only a single photo gracefully. Standard view's inline per-color table and Extended view's full table agreed exactly on every figure checked, including both correctly showing two rows for a color with two incoming inventory batches, and the favorite star plus the "Show Favorites" filter work correctly together end to end. Desktop's only real gaps: the color swatches don't highlight to show which color the arrows have navigated to, and clicking a swatch doesn't jump straight to that color's photo — it only opens the inline table. (This case's first pass had misread two behaviors as bugs — a non-functional Gallery view, and no way to see other colors at all — both corrected after review and verified directly; see the case file's Notes.) At tablet width, retested in Claude's built-in browser with true viewport emulation: the three View buttons (now labeled Gallery, "One column list", and Extended) are genuinely distinct here too, correctly adapted to the narrower width — Gallery shows two cards per row, One column list shows one full-width card per row, and Extended shows the full inline table per row, matching desktop's Extended content. Clicking a card's photo opens a full-screen image gallery (a separate feature from the detail drawer) with working left/right arrows and its own visible favorite star, confirmed paging correctly from Black into Dark Navy; hovering a card directly reveals the fullscreen icon and favorite star, same as desktop, just not the color-browsing arrows themselves — reaching another color at this width takes one extra click (into the gallery) rather than desktop's direct hover-paging. Both of the card's entry points into the detail drawer (the price-row icon, and clicking the card's own name/photo) were reconfirmed working correctly at tablet width too. This tablet section itself needed a correction along the way: a first pass had reported the three View buttons rendering identically and several hover controls as unreachable at 768px, which turned out to be a false reading caused by clicks not reliably registering during that first pass rather than a real product issue — caught by the UX Assessment Lead's direct question, and corrected after verifying each control's actual underlying state rather than just comparing screenshots. At mobile width, tested jointly with the UX Assessment Lead per the assessment methodology's standard approach for this browser's known sub-768px click limitation: the left nav collapses to a hamburger menu and the header favorites controls collapse into a "..." menu, as already seen in earlier cases; the View switcher moves inside that hamburger panel and drops the redundant "One column list" button, since Gallery already renders one full-width card by default at this width; the fullscreen icon and favorite star show on cards without needing hover (a nicer touch-appropriate adaptation than tablet's hover-only reveal); the full-screen image gallery, chevron table, and both drawer entry points all carry over correctly with matching data; and, as a genuine improvement over desktop and tablet, tapping a color swatch directly opens the drawer pre-scoped to that color. One small, cosmetic bug turned up along the way, caught by the UX Assessment Lead: the "..." menu lists "Show Favorites" twice — a real markup duplication (confirmed via the page's own code, including a duplicated HTML id), though both entries stay in sync and the feature itself works correctly either way. Before closing the case, the UX Assessment Lead flagged two icons by eye as feeling out of place — the card's drawer-entry "calculator" icon, and mobile's circled "..." icon — and both checked out as genuinely inconsistent once inspected in the page's own code: both are static image files rather than the inline, color-aware vector icons the rest of the app uses, the drawer icon's color is hard-coded and measurably different from its neighboring icons, and a check across the product found three different, unrelated "more options" glyphs (this one, a different one on Manage Reports, and Manage Users' edit-pencil icon from Case 04) rather than one consistent icon reused throughout. See the case file's Notes for the full account of both corrections and the icon-consistency finding.

### Case 07 — Adding to cart: quantities by size and color, and cart verification

**Status:** Case closed across desktop, tablet (768px), and mobile (375px) — five gaps found. The full journey works correctly end to end, identically at all three widths: browsing to a style, opening its detail drawer, entering different quantities across sizes and across colors, adding to cart, and verifying the cart matches exactly (right sizes, colors, quantities, prices, and totals). The app also enforces each size's real availability precisely — current stock plus a known future incoming batch, right down to the unit — before Add to Cart or Update Quantity can be clicked, reproduced at every width. A follow-up accessibility check on the same drawer (desktop only, by design) found that its color swatches have no keyboard path at all, and that its images lack `alt` text while its quantity fields and main action button show no visible focus indicator. Tablet testing also surfaced that the favorite star doubles as a cart-membership toggle — confirmed as deliberate business logic by the UX Assessment Lead, who also tested un-favoriting directly and found it doesn't actually remove the item from the cart, so it doesn't persist either (the star reverts to marked on refresh). A further check, prompted by the UX Assessment Lead's own observation and also desktop-only by design, found that the header's cart icon only appears while viewing the specific report/season where items were added, and disappears entirely on any other report — even with real, unsubmitted order value still sitting untouched elsewhere. Mobile testing added one more positive, mobile-specific finding: tapping a color swatch on the catalog card opens the drawer directly, pre-scoped to that color, consistent with Case 06. Priority: High overall (driven by the keyboard-inaccessible color swatches and the report-scoped cart icon); the other three findings are each Medium.

Walked through the "Adding items to the cart" journey on the Fall 2026 report, using "3/4 Sleeve Boatneck" (PA1136) in two colors. Opened the drawer, set S 3 / M 5 / L 2 / XL 4 for Black (14 units, $532.00) and, after switching color, XS 2 / M 6 / L 1 / XL 3 for Dark Navy (12 units, $456.00), adding each to the cart. The cart's "ORDER PREVIEW" screen matched both lines exactly, size by size and color by color, with a correct $988.00 / 26-unit total. A row's own "⋮" menu (Move To Another Delivery, Duplicate, Edit Quantity, Remove Color) worked correctly too — Edit Quantity reloaded the exact saved values, and Remove Color asked for confirmation before deleting a line. Before settling into the main flow, deliberately tested what happens when a typed quantity exceeds what's really available: numbers up to a size's true ceiling (current stock plus its known future batch — precisely 650 = 200 + 450 on one row) are accepted, but the number immediately past it turns the field's border red and disables the Add/Update button, with no text, tooltip, or accessible label anywhere explaining why or what the actual limit is — a real gap, since the only path to "fixing" it is noticing the color change and subtracting two other columns yourself. The drawer's "+" stepper controls (including a bulk stepper that applies to every size row at once) don't share this problem: driven 250 clicks past a size whose real ceiling was only 50, the field simply stopped exactly at 50 with no error ever shown, rather than letting an invalid number happen at all. Two separate guard dialogs — one when switching color with an unsaved quantity pending, one when closing the drawer mid-edit — correctly prevent quantities from being silently lost.

Before moving on to tablet and mobile, a targeted accessibility pass checked the same drawer's images and keyboard operability directly in the DOM. All 7 images inside the drawer (the main garment photo and 5 color-swatch thumbnails) have no `alt` attribute at all. The 5 color swatches are plain, non-focusable `<div>` elements — confirmed both by inspecting their properties and by a live Tab-key trace through the whole drawer, which jumps straight from the header icon buttons to the quantity fields without ever landing on a swatch: there is no way to change color in the drawer without a mouse. Quantities themselves can still be set by keyboard (typing, or the native arrow-key spinner on the number field), even though the custom "+"/"−" steppers are excluded from the tab order (`tabindex="-1"`) same as before. Focus visibility is inconsistent: the header icon buttons (close, info, favorite) keep the browser's default focus ring, but the 5 quantity fields and the main action button have `outline: none` with no replacement style, so tabbing to them gives no visible sign of where focus is.

The core journey (not the accessibility check) was then retested at 768px tablet width, using Claude's built-in browser with true viewport emulation. Every result matched desktop exactly: the same drawer-entry behavior, the same 99999-over-limit red-border/no-message gap reproduced on the S field, the same Black (14 units/$532.00) and Dark Navy (12 units/$456.00) quantities producing the same $988.00/26-unit cart total, the same "⋮" menu and Edit Quantity round-trip, and the same adaptive-column behavior for Dark Navy's zero-stock sizes. One observation from this pass turned into a real finding: Dark Navy's favorite star switched on by itself right after "ADD TO CART" was clicked, with no click on the star itself. The UX Assessment Lead explained this directly afterward: the star doubles as a cart-membership toggle — starring an item adds it to the cart at quantity 0 (creating a cart if none exists), and there's no separate place a "favorite" is recorded other than that cart presence, which is also why entering real quantities fills in the star as a side effect. A follow-up test by the UX Assessment Lead found that un-starring does *not* actually remove the item from the cart — the cart line stays, which is also why no confirmation dialog appears on that path — so the star reverts to marked once the report is refreshed. The finding that survives is a conceptual one (the star collapses two different user intents, bookmark-for-later vs. actually ordering, into one icon) plus a confirmed functional one (un-favoriting doesn't persist, since nothing about the underlying cart presence actually changes when it's tapped). See the case file's Finding 4 for the full usability reasoning and suggested direction, including what's still untested: un-starring a line that already has real, non-zero quantities.

One more check, again prompted directly by the UX Assessment Lead: does the header's cart icon reliably reflect the account's real cart state? Tested by adding 2 units of PA1136 Black/S to the Fall 2026 cart ($76.00), confirming the icon appeared, then switching to the Spring 2027 report without touching the cart — the icon vanished from the DOM entirely (not just hidden by CSS), even though the $76.00 line was still sitting untouched in Fall 2026's cart. Switching back to Fall 2026 brought the icon straight back. "MY ACCOUNT" → "Carts list" does correctly show a global, report-independent summary of open carts, but its own totals were unreliable in this same test ($0.00 and "-" for a cart the real Order Preview screen correctly totaled at $76.00), so it's an imperfect fallback at best. Testing also turned up a pre-existing, unrelated leftover in the Fall 2026 cart — "Long Sleeve Crew" (PA1182) favorited in all 5 colors at quantity 0, almost certainly residue from Case 06's own favorite-star testing, and confirmed by the UX Assessment Lead afterward as expected, harmless leftover, not something to clean up. See Finding 5 for the full usability reasoning: this is treated as High priority, since it's a gap in the primary, sitewide "you have an open order" indicator, not a rough edge in one drawer.

Finally, the core journey (not accessibility, not the cart-icon check) was retested a third time at 375px mobile width, using Claude's built-in browser, to close out this case. Every result again matched desktop and tablet exactly: the same 99999-over-limit gap reproduced with no explanatory message, the same Black (14 units/$532.00) and Dark Navy (12 units/$456.00) quantities producing the identical $988.00/26-unit cart total, and a working Edit Quantity round-trip via the mobile cart's own kebab-menu icon (visually distinct from desktop/tablet's, and requiring care to disambiguate one color row's menu from a neighboring one, but functionally identical once correctly targeted). Mobile also confirmed one small, positive difference already seen in Case 06: tapping a color swatch on the catalog card opens the drawer directly, pre-scoped to that color, rather than needing a separate drawer-entry tap. The built-in browser's click action reliably timed out at this width (a known limitation below tablet width), so every mobile interaction was driven via direct JavaScript clicks on the page's own elements instead, with screenshots used throughout to visually confirm each result — a testing-tool workaround, not a product issue.

Desktop used the UX Assessment Lead's own Chrome session; tablet and mobile both used Claude's built-in browser, at 768px and 375px respectively. The cart was restored to empty after the desktop, tablet, and mobile passes via "Remove Color" on every test line, and no order was ever submitted; the accessibility pass never added anything to the cart. Case 07 is now closed across all three viewports.

### Case 08 — Cart Editing / Order Placement

**Status:** Case closed, with desktop and tablet-width (768px) coverage confirmed and a mobile-width (375px) retest attempted but blocked, not completed — one significant retraction from desktop, two confirmed findings (one High, one Low — see below). Built multi-style, multi-color, multi-size cart test data and focused entirely on the "ORDER PREVIEW" cart page itself (not the add-to-cart drawer, already covered by Case 07), with delivery-date management as the primary focus. Every desktop finding and positive observation was confirmed to carry over unchanged at tablet width; the tablet pass additionally resolved Finding 2 from incomplete to fully confirmed.

**Retracted: the "Edit Delivery Dates" typed-input save failure.** An earlier draft of this case reported that typing a date directly into the panel's Start Date or X-Warehouse Date field and clicking Save silently fails to save it. This session's own automated browser testing reproduced that symptom repeatedly, including on a dedicated re-verification pass (prompted by the UX Assessment Lead first reporting they couldn't reproduce it) that pinned the mechanism down precisely: typing marks the field `ng-invalid` in Angular's own validation with zero visible sign of it, and Save's handler silently declines to call the API at all when invalid — confirmed via `read_network_requests` showing no request reaches `/api/carts/deliveries/*` on that path. But the re-verification's own reproduction didn't settle the question: the UX Assessment Lead then tested manually, more than once, with a real keyboard, and reports the field works correctly — a valid typed date saves, an invalid one shows a clear "Invalid Date" message — neither of which the automated testing ever saw. Given that direct, repeated conflict between automated and manual results, this is being retracted as a confirmed product defect, most likely explained by this session's browser-automation tool injecting text differently than a real keyboard does (skipping some per-keystroke or focus/blur behavior the field's validation depends on). The calendar-click path (select a day, click Save) was independently confirmed working correctly throughout, by both automated and manual testing. The case file carries the full account in its Notes section, including the underlying screenshots and DOM evidence — kept for transparency, not as a claim about real end-user behavior.

The two findings that stand independently of the above: "Move To Another Delivery" correctly blocks a move landing more than 30 days from an item's original date with a clear toast, but "Duplicate," reached through the exact same guided flow with the exact same auto-suggested default date, has no equivalent check at all — it silently creates an invalid, checkout-blocking cart line, discoverable only via a small warning icon's tooltip (High priority, confirmed at both desktop and tablet width, using two different auto-suggested date offsets). A second finding flags a per-color minimum-quantity indicator, left incomplete on desktop but fully confirmed on the tablet retest: threshold exactly 4 units per color, tooltip text "One or more colors are below the required color minimum.", and confirmed advisory-only — it never disables "Submit Orders" (Low priority). Quantity editing, line removal, delivery removal, and the checkout Season Minimum validation dialog all worked correctly. Priority: High overall, driven by the Duplicate finding.

"Add Delivery" auto-suggests a new delivery window starting the day after the prior one ends. Testing "Move To Another Delivery" through this default (both via drag-and-drop and the guided per-color menu) reliably triggered a clear block: "The item cannot be moved to a delivery date greater than 30 days from its original date," since the same 36-days-out default it auto-suggests already exceeds that window. Testing "Duplicate" through the identical guided path and identical default succeeded with no block or warning of any kind, creating a duplicated line whose only sign of trouble is a small orange "!" icon (tooltip: "This item cannot belong to the delivery you are currently in because the item's date is prior to the delivery date...") — confirmed to disable "Submit Orders" entirely. "Edit Quantity" and "Remove Color" both worked correctly and predictably, including Remove Color's own confirmation dialog working fine even on the already-invalid duplicated line.

With the cart back in a clean, valid state, and after explicit check-in and approval from the UX Assessment Lead for this specific checkpoint (an exception to this audit's general "Submit Orders is never clicked" rule, negotiated specifically for this case), "Submit Orders" was clicked once to observe the resulting validation: an "Opening Order Below Season Minimum" dialog, stating the exact dollar amount needed and that sales-management approval is required below that minimum. Attempting to click "Continue" from there (still within the scope of the approval given, intending only to observe the next screen and go no further) was blocked by this session's own automated safety guardrail, independent of the user's approval — no workaround was attempted; "Go back" was used instead to exit safely with no order ever finalized. All test-added lines and the extra delivery group were removed afterward, restoring the cart to empty.

**Tablet retest (768px):** run separately using this session's built-in browser pane (Claude in Chrome was unavailable after the desktop-testing logout incident), on the same "Fall 2026" report as desktop. Confirmed calendar-click delivery-date editing, the Move/Duplicate asymmetry (this time using a 15-days-out default rather than desktop's 36, for an even cleaner comparison), Edit Quantity's round-trip behavior, and both confirmation dialogs all work identically to desktop. Also confirmed a stricter, correct extension of the weekend-blocking date rule: the X-Warehouse date field disables every day of its own current month except the already-committed one. One tooling-only artifact surfaced and was resolved mid-session: this browser tool's screenshot-to-CSS-pixel coordinate ratio at the tablet preset measured empirically at ~1.094×, not the ~1.042× a naive calculation from the nominal viewport size would suggest — using the wrong ratio briefly looked identical to a genuine silent-click-failure bug until checked against a real click-event listener.
