# Case 07 — Adding to cart: quantities by size and color, and cart verification

**Status:** Case closed across all three viewports — desktop, tablet (768px), and mobile (375px). Five gaps found, all confirmed desktop-original issues that were then explicitly re-tested at the smaller widths (accessibility and the header cart-icon check were desktop-only by the UX Assessment Lead's own scoping, everything else was re-verified). The core flow works correctly end to end: browsing the catalog, opening a style's detail drawer, entering different quantities per size and per color, adding to cart, and verifying the cart holds exactly what was entered (right sizes, right colors, right quantities, right prices, right totals) all checked out identically on desktop, tablet, and mobile. The app also correctly prevents ordering more than a size's true available stock (current stock plus a known future batch) — but when that limit is hit by typing a number directly into the quantity field, the only feedback is a red border on the input, with no message anywhere explaining what happened or what the actual maximum is (reproduced at both tablet and mobile width too). The two "+ / −" stepper controls (per size, and the bulk "apply to every size" stepper) don't have this problem: they silently stop exactly at the true maximum instead of ever showing an invalid number. A follow-up accessibility check on the same drawer (desktop only, by design) found two further issues: the color swatches cannot be reached or operated with the keyboard at all (a complete dead end for choosing a color without a mouse), and the drawer's images have no `alt` text while its quantity fields and main action button show no visible focus indicator when tabbed to. Tablet testing also surfaced the favorite star's dual role as a cart-membership toggle — confirmed intentional business logic, not a bug, but with a usability read worth flagging (Finding 4). A follow-up check, prompted by the UX Assessment Lead's own observation, found that the header's cart icon is scoped to whichever report is currently open rather than to the account's real cart state — it disappears when switching reports even with real, unsubmitted order value sitting elsewhere (Finding 5, desktop only, by design). Mobile testing additionally confirmed a positive, mobile-specific adaptation: tapping a color swatch on the catalog card opens the drawer directly, pre-scoped to that color — consistent with Case 06's mobile findings.

**Priority:** High overall, driven by Finding 2 (color swatches have no keyboard path at all) and Finding 5 (the primary cart-status indicator hides real pending order value the moment you switch reports). Findings 1, 3, and 4 are each Medium — see each finding's own priority note for reasoning.

## Scope

- **Area:** Cognitive walkthrough of the "Adding items to the cart" journey: browsing the catalog to a style, opening its detail drawer, selecting different quantities across sizes and across colors, adding to cart, and verifying the resulting cart line by line. Also includes a targeted check of what happens when a requested quantity exceeds what's actually available for a size, an accessibility spot check of the same drawer (image `alt` text, keyboard reachability and operability of its controls, and focus visibility), a check of the favorite star's coupling with cart membership, and a check of the header cart icon's visibility behavior when switching between reports/seasons.
- **Screen:** `/reports/3771` (the Fall 2026 linesheet report, same as Cases 02 and 06) → the style detail drawer for "3/4 Sleeve Boatneck" (PA1136) → `/my-account/cart` (the "ORDER PREVIEW" cart screen).
- **Interaction boundary:** Tested using the user's own real, already-authenticated Chrome session. Added real quantities to the real cart for one style across two colors (Black and Dark Navy), verified the resulting cart line by line, then removed both lines afterward via the cart's own "Remove Color" action (confirmed via its own confirmation dialog) to leave the shared test account as it was found. **"Submit Orders" was never clicked** — no order was placed. Deliberately tested entering quantities beyond a size's real availability (up to 99999 on one row) to see how the app responds; these excessive values were corrected before ever calling Add to Cart, so nothing invalid reached the cart itself.
- **Session:** Seventh case of this audit round. Started desktop only, per the UX Assessment Lead's explicit request to start with the desktop version using their own Chrome. The core add-to-cart journey (not the accessibility check) was then retested at 768px tablet width and, finally, at 375px mobile width, both using Claude's built-in browser with true viewport emulation. Accessibility and the header cart-icon check (Finding 5) were desktop-only by explicit design, not oversight. Case 07 is now closed across all three viewports.

## Steps — accessibility spot check on the drawer (images and keyboard navigation)

Per the UX Assessment Lead's request, before moving on to tablet and mobile for this same case, a focused accessibility pass was run on this same style detail drawer (PA1136, Black), checking two things: whether the drawer's images have meaningful `alt` text, and whether the drawer's controls can be operated with the keyboard alone. This was done by inspecting the live DOM directly (`img.alt`, `tabIndex`, computed focus styles) rather than relying on visual inspection alone, and by driving real Tab / arrow-key presses and reading `document.activeElement` after each one.

- Inspected every `<img>` element inside the drawer (7 total): the main garment photo and 5 color-swatch thumbnails all have **no `alt` attribute at all** — not even an empty `alt=""` marking them as decorative. Screen readers fall back to reading the image filename or announcing "image" with no useful content in this case.
- Inspected the 5 color swatches (`.sku-color` — Black, Dark Navy, Heather Grey, Rope, White): each is a plain `<div>` with the color name only in a `title` attribute (a hover tooltip, not a reliable accessible name for a non-native control) — no `role="button"`, no `tabindex`, no `aria-label`. Confirmed via `tabIndex` inspection that none of the 5 are keyboard-focusable at all.
- Built a full list of the drawer's actually keyboard-focusable elements (`tabIndex >= 0`): 10 total — the close button, the info ("i") button, the favorite (star) button, one more small icon button near the photo, the 5 per-size quantity `<input>` fields, and the main action button (SELECT QUANTITY / ADD TO CART / UPDATE QUANTITY). Separately confirmed that all 12 of the drawer's custom "+" / "−" stepper controls (5 rows × 2, plus the 2 bulk-apply steppers) are `<div>` elements with `tabIndex="-1"` — explicitly excluded from keyboard navigation.
- Drove a live Tab-key trace through the drawer, reading `document.activeElement` after each press, starting from the close button: close → info → favorite → (a small unlabeled icon button) → XS quantity → S → M → L → XL → action button. The 5 color swatches are never visited — confirmed both by the static `tabIndex` check and by this live trace, which jumps directly from the last header icon button to the XS quantity field. **A keyboard-only user cannot change the drawer's color at all.** Screenshot: `08-color-swatches-plain-divs-not-focusable.png`.
- Tested whether the quantity itself can still be set without a mouse, since the custom steppers are unreachable: typing a number directly into a focused quantity field works exactly as it does with a mouse (confirmed earlier in this case), and the field's native browser behavior also responds to the Up/Down arrow keys (confirmed: focused a field at 0, pressed Up, value became 1). So quantities can be set via keyboard, just not via the custom stepper buttons themselves.
- Confirmed that the action button correctly enters and leaves the tab order based on its real `disabled` state: with every size at 0 it's skipped entirely (native `disabled=true`, not just styled to look inactive); after typing a valid quantity into a field, it becomes enabled and is reachable by Tab immediately after the last quantity field, in the expected reading order.
- Checked focus visibility by reading each focused element's computed `outline` / `box-shadow`. The three header icon buttons (close, info, favorite) keep the browser's own default focus ring (a visible dark outline, confirmed both in computed styles and in a screenshot — `06-drawer-close-button-visible-focus-ring.png`). The 5 quantity `<input>` fields and, notably, the main action button itself all have `outline: none` with no alternative focus style (no box-shadow, no border-color change) — focusing them produces no visible change at all, confirmed both via computed style (`outlineStyle: "none"`) and by screenshot (`07-add-to-cart-button-no-visible-focus-indicator.png`, taken with the ADD TO CART button focused and enabled).
- All values were reset to 0 before any Add to Cart call in this part of testing, so no cart line was created and no cleanup was needed; the drawer was then closed normally.

## Findings

### Finding 1 — Exceeding a size's real availability by typing a number gives no explanation anywhere, only a red border

Every size in the drawer's quantity table has a real, enforced maximum equal to its current "Available" figure plus its known future "Aug 01" batch (confirmed precisely: 650 = 200 + 450 is accepted, 651 is not). Typing a number above that maximum is accepted into the field, but the moment it crosses the line, the input's border turns red and both "ADD TO CART" and "UPDATE QUANTITY" become disabled — with no text message, tooltip, or accessible label anywhere in the drawer saying what happened or what the actual maximum is. A user has to notice the color change, then manually add the "Available" and "Aug 01" columns themselves to figure out what number would actually be accepted.

This is inconsistent with how the drawer's own "+" stepper controls handle the same limit: clicking "+" enough times on a row never produces an invalid number at all — it simply stops incrementing exactly at the true maximum, with no error state ever shown, confirmed directly by driving the bulk "apply to every size" stepper 250 clicks past a size whose real ceiling was only 50. The stepper path prevents the error before it happens; the typing path lets the user hit it, then leaves them to self-diagnose it.

**Heuristic relevance:** Visibility of system status (the interface has the exact maximum — it enforces it precisely — but never displays it); recognition, diagnosis, and recovery from errors (there's no explanation to recognize or diagnose, and recovery means doing the subtraction yourself); reliance on color as the only signal (a colorblind user, or anyone not looking closely at the field's border, would have no way to notice the field is even in an error state).

**Suggested direction:** Add an inline message near the field when it's over the limit — for example "Maximum available: 650" — and wire it to the input via `aria-describedby` (or a `role="alert"` region) so it's not conveyed by color alone. Since the "+" stepper already knows the exact ceiling and enforces it silently, the same value is available to power an explicit message on the typing path too, rather than building new logic for it.

**Priority note:** Medium — the cap is genuinely enforced and no bad data can reach the cart, but this will be hit routinely on a frequent, everyday flow (adding a multi-size order to cart) any time inventory is tight, and currently offers no way to recover from it except guesswork.

### Finding 2 — The color swatches in the drawer cannot be reached or operated with the keyboard at all

The 5 color swatches in the drawer (Black, Dark Navy, Heather Grey, Rope, White for this style) are plain `<div>` elements with no `tabindex`, no `role="button"`, and no `aria-label` — confirmed by inspecting every swatch's properties and by a live Tab-key trace through the whole drawer, which skips straight from the header icon buttons to the first quantity field without ever landing on a swatch. There is no keyboard equivalent offered anywhere else in the drawer for switching color. A keyboard-only user — someone using Tab/Enter instead of a mouse, whether by necessity (a motor impairment, a screen reader) or by preference — can open the drawer, read the default color's photo and price, and set quantities for that one color, but cannot reach any of the style's other colors from the drawer at all.

**Heuristic relevance:** Accessibility / keyboard operability (a core interactive control has no keyboard path); this also affects anyone who simply prefers keyboard navigation for speed, not only assistive-technology users.

**Suggested direction:** Give each swatch a real interactive role — either a native `<button>` or a `<div role="button" tabindex="0">` with an `aria-label` built from the color name already available in the existing `title` attribute (e.g. "Dark Navy") — and wire Enter/Space to the same click handler already in place. The color name is already present in the markup for the tooltip, so this is primarily a markup/semantics fix rather than new logic.

**Priority note:** High — this isn't a rough edge on an already-reachable control, it's a complete keyboard dead end on a control with no alternative path, blocking a core action (choosing which color to order) for anyone who can't use a mouse.

### Finding 3 — The drawer's images have no `alt` text, and its two most-used controls (quantity fields, the main action button) show no visible focus indicator

All 7 `<img>` elements inside the drawer — the main garment photo and the 5 color-swatch thumbnails — have no `alt` attribute at all (not even an empty `alt=""` to mark them as decorative), confirmed by inspecting the DOM directly. A screen reader has nothing to announce for the garment photo itself, which is the one image in the drawer that actually carries information (what the garment looks like in the selected color) — the swatches are a smaller loss on this specific point, since their color name is already exposed via `title`, but `title` is not a dependable substitute for `alt` or `aria-label` either.

Separately, focus visibility is inconsistent across the drawer's 10 keyboard-focusable elements. The 3 header icon buttons (close, info, favorite) keep the browser's default focus outline, so a keyboard user can see where they are. But the 5 quantity `<input>` fields and — more importantly — the main action button (ADD TO CART / UPDATE QUANTITY / SELECT QUANTITY when enabled) all have `outline: none` in their computed styles with no replacement focus style, confirmed both by computed style and by screenshot (`07-add-to-cart-button-no-visible-focus-indicator.png`, taken with that exact button focused). A keyboard user typing quantities and tabbing to submit has no visual confirmation of where their focus is for the two things they're actually doing in this drawer.

**Heuristic relevance:** Accessibility (missing accessible names for informative images; visibility of system status for keyboard focus, which the WCAG "Focus Visible" criterion treats as a baseline requirement, not a nice-to-have).

**Suggested direction:** Add a descriptive `alt` (e.g. "3/4 Sleeve Boatneck, Black" for the main photo, ideally including the style name and color already available in the surrounding markup) to the garment photo, and either `alt=""` (if purely decorative given the adjacent color-name text) or a matching descriptive `alt` to each swatch thumbnail. For focus visibility, restoring a visible `:focus-visible` style (an outline or box-shadow, consistent with what the header icon buttons already show) to the quantity inputs and the action button would close the gap without needing a new visual language — the header buttons already demonstrate the pattern the rest of the drawer is missing.

**Priority note:** Medium — neither issue blocks a sighted mouse user, but together they make the drawer meaningfully harder to use with a screen reader or keyboard alone, on top of Finding 2's complete color-switching dead end.

### Finding 4 — The favorite star doubles as a cart-membership toggle, and un-favoriting doesn't actually persist

This one isn't a bug in its core design — it's a deliberate business decision, explained directly by the UX Assessment Lead after this case surfaced it as an unexplained observation during tablet testing: the star icon doesn't only mark a style or SKU as a favorite. Tapping it adds the item to the cart (creating an empty cart first if none exists) at quantity 0, and there's no separate, independent place a "favorite" is recorded — the star's state is entirely derived from whether the item currently has a line in the cart. Entering real quantities manually has the same underlying effect, which is why doing so also fills in the star automatically, even though the user never touched it — confirmed directly in this case's tablet pass (Dark Navy's star was unfilled immediately before "ADD TO CART" and filled immediately after, with no click on the star itself in between).

*Correcting an earlier draft of this finding:* the first version of this write-up assumed tapping the star again to un-favorite would remove the item from the cart — the same effect as "Remove Color" — and worried about that happening with no confirmation dialog, risking silent loss of real order quantities. The UX Assessment Lead tested this directly afterward and found that's not what actually happens: un-starring an item does **not** remove it from the cart. The cart line stays exactly as it was. That's also *why* no confirmation dialog appears when un-starring — nothing is actually being removed, so there's nothing to confirm. The visible effect is that the star appears to un-mark in the moment, but since favorite status has no home other than cart presence, and the cart presence never actually changed, refreshing the report shows the star back to marked. So the real defect isn't a data-loss risk — it's that the un-favorite action doesn't do what it visually claims to do.

From a usability standpoint, two separate issues are worth flagging here, independent of whether reusing the cart as the storage mechanism for favorites is a reasonable engineering shortcut — it may well be:

First, the conceptual one: a star is one of the most standardized icons in software — across virtually every catalog, marketplace, and B2B ordering tool a wholesale buyer has ever used, it means "save this for later, bookmark it, remember it," a lightweight, low-stakes, purely personal curation action, deliberately separate from actually acquiring or ordering the item. Here it means something functionally different: "this item now has a presence in your cart." Those are two different user intents — browsing/curating versus transacting — and collapsing them into one icon means a Sales Rep can't do the first without triggering the second. Every style they star to "keep an eye on" while browsing silently becomes a zero-quantity cart line; every style they actually order (by typing quantities) silently gets tagged as a personal favorite whether they meant to bookmark it or not. Over time this is likely to make "Show Favorites" (from Case 06) less useful as a curation tool, since it fills up with every style ever ordered, not just the ones a rep deliberately chose to flag.

Second, the confirmed functional one: un-favoriting doesn't persist. A Sales Rep who taps a star to clear it from their favorites — believing, reasonably, that this is what the toggle does — will see it revert to starred the next time the report loads, with nothing telling them why or that it happened at all. That's a broken feedback loop: the interface shows one state right after the click, and a different, contradicting state on the next visit, for a control whose entire job is to reflect a simple on/off preference. It's a smaller-stakes problem than the data-loss scenario this finding originally raised, since no order quantities are actually at risk in the specific case tested (a zero-quantity, favorite-only line) — but it still means the "remove from favorites" action is effectively non-functional today. What still hasn't been tested by either of us is the case with real stakes: un-starring an item that already has non-zero quantities entered. Does the star even offer to un-favorite in that state, given the cart line legitimately needs to stay for the order to remain intact? Or does it attempt the same no-op and just fail to update, the same way it does for a bare zero-quantity favorite? That's the scenario worth a dedicated, careful check before this finding can be considered closed.

**Heuristic relevance:** Match between system and the real world (the star's meaning departs from the near-universal convention it borrows its icon from, and now also from what un-starring visibly appears to do); visibility of system status (the UI shows a state change on click that doesn't match the persisted state, discoverable only by refreshing); user control and freedom (a rep has no working way to remove a style from their favorites once a corresponding cart line — even an empty one — exists).

**Suggested direction:** Decide, first, whether un-favoriting an empty (quantity-0) cart line is *supposed* to remove that line — if so, this is a straightforward functional bug to fix in the un-star handler; if favorite lines are meant to persist in the cart regardless of the star's state, then the star's on/off affordance is misleading and shouldn't visually promise a toggle it can't deliver. Separately, and regardless of that decision: if favoriting and cart-membership need to stay technically linked, consider giving them visually distinct affordances so a rep can tell, at a glance, whether a control touches their real order — for example, keeping the star as a pure bookmark concept and using a separate, cart-specific indicator for "this item has a cart line." The existing "i" info icon already present in the drawer's header could also disclose the relationship in a line or two, so it's discoverable without needing to be explained directly, the way it had to be here.

**Priority note:** Medium. Lower than this finding's first draft, now that testing has ruled out the silent-data-loss scenario for the case actually tested — but a favorite toggle that silently fails to persist is still a real, confirmed, user-facing defect, not just a judgment call, and the untested real-quantity scenario could still turn out to matter more once checked.

### Finding 5 — The header cart icon is scoped to whichever report is currently open, not to whether there's anything pending anywhere in the account

Prompted by the UX Assessment Lead's own observation while browsing: the small cart icon next to the search icon in the header (the one that opens "ORDER PREVIEW") isn't a simple "cart has items" indicator. It's scoped to the specific report/season currently being viewed. Confirmed directly, step by step: with the cart genuinely empty, the icon is absent from the page entirely (not hidden by CSS — `document.querySelector('.cart-icon-button')` returns `null`, the element isn't rendered at all). Added 2 units of "3/4 Sleeve Boatneck" (PA1136), Black, size S to the Fall 2026 cart ($76.00): the icon appeared immediately while still on the Fall 2026 report. Switched to the Spring 2027 report (a different linesheet/season) without touching the cart: the icon disappeared completely, even though the $76.00 line was still sitting in the Fall 2026 cart, untouched. Switched back to Fall 2026: the icon reappeared. The underlying cart data never changed across any of this — only the icon's presence did, tracking the currently-open report rather than the account's real cart state.

Along the way, this also surfaced that the Fall 2026 cart already held a pre-existing, real entry unrelated to this test: "Long Sleeve Crew" (PA1182), favorited in all 5 of its colors, each sitting at quantity 0 across every size — 25 zero-value rows, visible directly on the "ORDER PREVIEW" screen (every cell reads 0, every color's total reads $0.00). This is almost certainly left over from Case 06's own testing of the favorite star and "Show Favorites" filter, never cleaned up afterward — flagged in Notes rather than removed unilaterally, since it wasn't part of this test and the account is shared.

There is a second, global way to check for pending cart activity regardless of which report is open: "MY ACCOUNT" → "Carts list" in the left navigation, which correctly listed "Fall 2026" as an active cart (with an accurate item count) while the header icon was hidden on Spring 2027. But this fallback has its own credibility problem: its "TOTALS" column showed **$0.00**, and the expanded delivery row showed an "Amount" of **"-"**, for a cart that the real Order Preview screen — reached through the very same account, moments apart — correctly totaled at **$76.00**. So even the one place designed to answer "do I have anything pending elsewhere" gets the dollar figure wrong, which is very likely the number that actually matters to a rep deciding whether to go finish something.

From a usability standpoint: a cart icon's whole job, in essentially every ordering or e-commerce interface a wholesale buyer has used, is to give a persistent, always-visible answer to "do I have anything pending right now" — that's reinforced here by the fact that this icon does show live cart content, not a generic notification. Scoping its visibility to the currently-open report undermines that job in exactly the situation where a B2B wholesale tool like this one is used most: a rep working across several seasons in one sitting (this account alone lists Spring 2027, Holiday 2026, Fall 2026, and In Stock as separate linesheets). Someone who builds a real, valuable order under Fall 2026, then moves on to browse Spring 2027 to start a second one, gets no visual reminder at all that the first order is still open and unsubmitted — the header doesn't stay silent or neutral about it, it actively signals "nothing pending," which is false.

**Heuristic relevance:** Visibility of system status (the true state — real money pending in a cart — doesn't change when switching reports, but the interface's only persistent signal for that state does, and it flips to imply the opposite of what's true); consistency (the same fact, "you have an open cart," is shown accurately in one place — the Order Preview itself — and inconsistently or wrongly in the two others that exist to summarize it, the header icon and Carts List's totals).

**Suggested direction:** Make the header cart icon reflect the account's cart state globally — present whenever any report/season has a pending cart, not only the one currently open — the same way "Carts list" already correctly detects a Fall 2026 cart while Spring 2027 is on screen; the underlying check clearly exists somewhere already. If the underlying architecture genuinely ties a cart to a single report and the icon can only reasonably reflect the open one, then a secondary, lightweight signal belongs somewhere in the persistent chrome (a badge on "MY ACCOUNT," or on the linesheet switcher itself) so a rep browsing report B can tell "you left something in another report" without already knowing to check Carts List. Separately, and regardless of that decision: Carts List's totals should be fixed to match what Order Preview already computes correctly for the same data — a dash and a $0.00 for a cart that's actually worth $76.00 undermines the one screen meant to be trustworthy about this exact question.

**Priority note:** High. This isn't a rough edge inside one drawer — it's a gap in the primary, sitewide indicator for "you have an open order," for what looks like the normal way this product gets used (a rep working across multiple seasons in one session, not just one linesheet at a time). A missed or forgotten cart is the kind of thing that turns into a real business cost — an order that should have shipped and didn't — not just an inconvenience.

## Positive observations

- The full journey — browse the catalog, open a style's drawer, enter different quantities across multiple sizes and multiple colors, add to cart, and verify — worked correctly end to end, with the cart matching the drawer exactly on every figure checked: per-size quantities, per-color subtotals, and the cart's own grand total (26 units, $988.00 across the two colors tested).
- The app enforces each size's real availability precisely — current stock plus a known future batch, right down to the unit (650 accepted, 651 rejected) — which is a meaningful, correctly-implemented business rule, not just a cosmetic check.
- Two separate guard dialogs ("Add to Cart Not Added" when switching color with a pending, unsaved quantity; "Quantity Changes Not Applied" when closing the drawer mid-edit with unsaved changes) proactively protect against silently losing entered quantities — a genuinely good, consistent safety net across two different moments in the flow.
- The bulk stepper (increment or decrement every size in the table by one, in a single click) is a fast, well-built shortcut for a common wholesale pattern — ordering one of each size — and correctly respects each size's own individual cap even when applied in bulk, never producing an invalid value.
- The cart's per-line "⋮" menu (Move To Another Delivery, Duplicate, Edit Quantity, Remove Color) is a complete, sensible set of controls for managing a line after adding it; "Edit Quantity" correctly reloads the exact saved quantities, and "Remove Color" asks for confirmation before actually deleting a line.
- The "ADD TO CART" button's label changes contextually and correctly through the whole lifecycle of one interaction — "SELECT QUANTITY" (disabled, nothing chosen) → "ADD TO CART" (enabled, ready) → "ADDED TO CART" (disabled, just added) → "UPDATE QUANTITY" (enabled, once an already-saved line is actually edited) — which is a small but genuinely helpful bit of status communication.
- A color with zero current stock in every size (Dark Navy, here) simply drops the "Available" column from its table entirely rather than showing a column full of zeros — a sensible adaptation rather than visual noise, consistent with the adaptive-column pattern already seen in Case 06.
- The empty-cart state ("You don't have items for this delivery yet — You can drag them from other deliveries") is clear and even hints at a drag-and-drop capability between deliveries, not tested in this case.
- Quantities can be set entirely by keyboard even though the custom "+"/"−" steppers themselves aren't focusable: typing a number directly into a field works exactly as with a mouse, and the field also responds to the native Up/Down arrow-key spinner behavior browsers give `type="number"` inputs — so the one control that's actually essential to this journey (setting a quantity) does have a keyboard path, even though the shortcut buttons for it don't.
- The main action button correctly uses the native `disabled` attribute (not just a disabled-looking style) to control both its clickability and its presence in the keyboard tab order — with everything at 0 it's properly skipped by Tab, and it becomes reachable again the moment a real quantity makes it valid, in the expected reading order after the last quantity field.
- The 3 header icon buttons (close, info, favorite) keep the browser's own default focus ring, proving the app isn't globally suppressing focus styles — the gap in Finding 3 is specific to the quantity fields and action button, not a site-wide pattern, which should make it a narrower fix.
- The entire core journey — drawer entry, the availability-limit cap, entering distinct quantities per size and color, adding to cart, cart verification, the "⋮" menu, and the Edit Quantity round-trip — behaves identically at 768px and on desktop, with the same numbers, the same guard behavior, and the same adaptive-column pattern for an out-of-stock color. Nothing about the tablet layout introduced a new gap or hid a control that desktop exposed.
- The same journey holds up at 375px mobile width too: identical quantities, identical cart totals ($988.00/26 units), identical availability-limit behavior, and a working Edit Quantity round-trip via the mobile cart's own kebab-menu variant. Mobile also adds a small, sensible improvement of its own: tapping a swatch on the catalog card opens the drawer directly pre-scoped to that color, rather than requiring a separate drawer-entry tap as on desktop and tablet — a touch-appropriate simplification, not a shortcut that hides functionality.
